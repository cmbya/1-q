# 京东登录成功后无法导入：响应分类与诊断补充

基线：`4d72ca1468755492c591eaa29f98103bc85f6a8f`。本轮修复已证实的错误分类缺口，并补足下一次真机排查所需的结构信息；不宣称已恢复真实账号订单读取。

## 用户日志能够证明的事实

- 2026-11-04 12:09:25（Asia/Shanghai）：登录验证接收了结构化桥接结果，随后完成会话保存。
- 12:09:27：用户主动读取时重新加载订单页。
- 12:09:28：HTTP 状态为 200，但捕获脚本报告 `responseSchema`，没有接收有效订单桥接结果；DOM 也未识别订单。
- 12:09:47：此次读取失败。HTTP 200 只能证明传输成功，不能证明拿到了成功的订单列表。
- 较早 09:07:46 的记录是另一种情况：扫描 10 笔，9 笔缺少可信下单日期、1 笔被业务筛选排除。不能把这个历史结果当作 12:09 的实际响应。

原日志没有记录是哪一层结构不匹配，也没有原始响应；无法据此断定是账号过期、风控、接口变化或其他业务错误。导航被拒绝也出现在验证成功的过程中，不能仅凭该事件认定它是主因。

## 已核实并修正的缺口

匿名读取京东公开订单页脚本 `https://jstatic.3.cn/order/js/5.83c444a16e0a3454edec.js`：其请求处理检查 `body.errorCode`，其中 `302` 进入登录处理；列表组件在读取 `orderList` 前区分业务错误。该脚本也处理顶层 `retcode`。未使用真实账号、Cookie 或账户接口。

原捕获脚本只检查顶层 `code/success`，遗漏业务错误封装。结果可能是把业务错误误报为结构错误，甚至在错误对象同时带空列表时接受为空订单。

本轮修改：

1. 识别已知订单接口的 `body.errorCode=302`，归为认证失败；其他业务错误与非零 `retcode` 保留为 `interface`，不接受其中的空列表。
2. 区分响应根对象、业务体、列表缺失/类型/长度/行结构问题，不尝试猜测未知字段或递归搜索任意数组。
3. 从脚本到原生日志只传递固定、限幅的数字分类，不记录接口原始错误码、错误文案、URL、Cookie、订单或商品内容。
4. 保留原始失败阶段，避免 `jdOrdersParse` 在外层日志中变成 `jdPageDOM` 或 `jdFetch`。
5. 正常列表、后续有效响应、分页、日期筛选和运单校验保持原流程；没有复用登录时的旧列表、取消日期限制、自动重试或改用付费接口。

## 新诊断字段

| 字段 | 值的含义 |
| --- | --- |
| `jdRequestKind` | 0 未知，1 手机列表，2 PC 列表，3 手机日期详情，4 手机物流，5 PC 物流 |
| `jdRootType` / `jdBodyType` / `jdListType` | 0 缺席或尚未检查，1 null，2 boolean，3 number，4 string，5 array，6 object |
| `jdSchemaStep` | 1 根对象无效，2 业务体无效，3 缺少列表，4 列表类型错误，5 超过 200 行，6 非空列表没有对象行 |
| `jdBusinessSource` | 1 顶层 code，2 retcode，3 success=false，4 body.errorCode；不是上游实际错误码 |
